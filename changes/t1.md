# T1 fragment (for the main session to merge into the SDD, the catalog, package.json and the changelog)

## SDD changes

- Section "Lanes": the live lane is the TypeScript port in a dedicated Web Worker (`frontend/src/engine/holo/`), held to the Python
  engine by vitest parity tests on `tests/fixtures/engine/*.json` (catalog row engine-reference, written by
  `data-pipeline/pipeline/stages/engine_reference.py`). The ported methods are exactly those whose Python `SPEC.lane` is `live` or
  `both`: M01 to M08, M10, M11, M12, M14, M15, M16, M19 (15 methods). B1 and B2 are `baked` in E3's specs (not live); M09, M13, M18,
  B4, B5 are baked; B3 inference is U2b's. Every other id raises `NotLive` ("replayed from the bake"), never a fallback.
- Section "Lanes", measured numbers (Chromium 153.0.8010.12 driven by Playwright 1.63, i9-14900HX laptop, 30 iterations of M07 on the
  256 x 256 padded-2 grid, a warm run, in the worker, CPU path, whole run including the scoring from the final phase):
  C02 (100 off-bin traps, the default case; point form) 0.49 to 0.80 s depending on the browser mode and the machine load, inside the
  1500 ms lane budget; C03 (1024 off-bin traps) 2.4 to 4.3 s, outside it (Node on the same machine: 0.55 s; the factor between the
  worker and Node is a measured variance of this laptop, as in R2 D5). The exact figures per run are in the T1 report.
  WebGPU (Intel gen-12lp adapter, new headless mode only): 30 iterations of M07 on the same cases with traps moved to FFT bins take
  0.31 to 0.32 s against 1.5 to 1.6 s on the CPU in that mode (5 times), agreement with the CPU path 3e-5 rad (one iteration),
  5e-7 in efficiency and 9e-5 relative in the trap intensities (thirty iterations).
- Section "Resources": the point-trap plan caches the x factors of the column groups and the y factors of every trap
  (`M n <= 2e6` values, 32 MB at most) for the length of a run; the GPU path holds two `nFft^2` complex float32 buffers (4 MB at
  512 squared) and a few trap-sized buffers, released when the run ends or is cancelled.
- Section "ADR fit", WebGPU extension row: the gates of ADR-0069 A69.7 are parity (`AGREEMENT_TOL` 2e-3 of the mean trap intensity
  inside the run, rejected otherwise; the browser agreement test of `scripts/engine-browser.mjs`), latency (the timings above),
  memory (above) and fallback (every absent, ineligible or failing GPU run takes the CPU path and records the reason in
  `RunResult.fallbackReason`; an explicit `backend: 'cpu'` records none). The GPU path covers the FFT-form iterations of M04, M06 and
  M07 for ideal-device point traps on FFT bins with z = 0 and no vortex; everything else is CPU.
- Section "Methods", M07: its Python default `form='fft'` needs traps on FFT bins, and the records C02, C03, C06 and C07 of
  `data/examples/cases.json` have off-bin traps (largest offset 0.28 bin for C02, 0.98 for C03), so
  `infer.run_method(C02_grid_feedback, 'M07')` raises `the fft form needs traps on FFT bins`. The TypeScript client selects the point
  form for M07 when the traps are off the bins (identical on bins) and says so in the report; whether the bake should do the same or
  snap the case traps is the main session's decision.
- Section "Engine API" (new): `createEngineClient()` in `frontend/src/engine/holo/client.ts`, the names and shapes the workbench
  unit uses, with these additions: `RunRequest.options.extra` (method keywords), `RunResult.timing`, `EngineClient.gpu()`, and for the
  particle simulation `ParticleRequest.phase`, `params`, `trap`, `setup` (the exact local map needs the phase and the case; the
  focal-only form interpolates the sampled intensity and is an approximation).

## package.json (shared; not edited by T1)

No new dependency: `fft.js` 4.0.4 (pinned), `playwright`, `vite` and `vitest` are already declared. Suggested script for the gate run:
`"engine:browser": "node scripts/engine-browser.mjs --assert"` (set `PLAYWRIGHT_BROWSERS_PATH` to the temp root's `ms-playwright`;
`--mode shell` exercises the WebGPU-absent fallback, `--mode chromium` the GPU path).

## Test paths

`frontend/src/engine/holo/{core,device,methods}.parity.test.ts` (parity against the Python fixtures), `worker.test.ts` (protocol,
cancellation, progress, transferables, NotLive over a loopback), `tests/contracts/test_documents.py` block "engine-reference"
(schema, example, array sizes, coverage of every live method, reproducibility of the fixtures from the Python engine),
`frontend/scripts/engine-browser.mjs` (real Worker and WebGPU in Chromium, local and in the gate run, never in Node CI).
